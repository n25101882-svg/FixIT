## Реалізований сценарій

MASTER із `/dashboard` відкриває «Профіль і послуги» (`/master/services`). Переглядає й редагує власні city, основну category та description; name — тільки для читання. Створює й редагує Service title/category/description/priceEstimate, приховує/активує через isActive. Зміни відображаються без F5. Немає полів редагування email/password/role/isApproved, approval workflow чи фізичного DELETE.

Кожна послуга має власну категорію, незалежну від основної категорії MasterProfile. Порожні необов’язкові опис/ціна передаються як null; priceEstimate зберігається Decimal(10,2), нуль відрізняється від невідомої ціни. Field errors пов’язані через aria-describedby; помилки збереження не скидають введені значення. Неоднозначний результат (мережа/5xx/409) блокує наступну мутацію до явного GET; POST автоматично не повторюється. 401 завершує чинну сесію, 403 блокує керування.

Публічна головна `/` веде до `/catalog`. Сервер виконує фільтрацію за містом, категорією послуги та текстом; браузер отримує сторінку, а не всі записи. Картка містить назву, категорію, короткий опис, майстра/місто й відому ціну або «Ціна за домовленістю». `/masters/:id` показує основну категорію/опис майстра та його активні послуги. Профіль публічний навіть із порожнім active-списком; isApproved лишається internal legacy, не новий approval gate.

Гостьові URL каталогу/профілю працюють після F5 без входу. MASTER/CLIENT сторінки й in-memory JWT збережені; F5 приватного кабінету надалі потребує login (FIX-17). Кнопка «Замовити послугу» **disabled**, має actual serviceId на картці й пояснення майбутньої доступності. US-04/створення STANDARD не реалізовані; browser перевіряє відсутність Order для нової послуги.

## API-контракти

Prefix `/api/v1`. Private routes — Bearer JWT і поточний MASTER із профілем; identity тільки JWT → User → MasterProfile. Public GET не проходять CLIENT/MASTER authentication й не повертають User.id/email/passwordHash/JWT/isApproved/audit/order data. Public frontend не додає Authorization до цих GET навіть за наявності локальної сесії.

| Маршрут | Вхід | Успіх |
| --- | --- | --- |
| GET `/master/profile` | Без query/body | 200 `{profile}` |
| PATCH `/master/profile` | Непорожня підмножина city/category/description | 200 `{profile}` |
| GET `/master/services` | Без query/body | 200 `{services}` — усі власні, включно з прихованими |
| POST `/master/services` | title/category; optional description/priceEstimate/isActive | 201 `{service}` |
| PATCH `/master/services/:id` | UUID, непорожня підмножина тих самих полів | 200 `{service}` |
| GET `/catalog/services` | optional city/category/q/page/limit | 200 `{services,page,limit,total,totalPages}` |
| GET `/catalog/masters/:id` | MasterProfile UUID, optional page/limit | 200 `{master,services,page,limit,total,totalPages}` |

Приклад створення послуги:

```json
{
  "title": "Ремонт змішувача",
  "category": "PLUMBING",
  "description": "Діагностика та ремонт",
  "priceEstimate": "250.50"
}
```

Приховати: `{"isActive":false}`, активувати: `{"isActive":true}`. Очистити ціну: `{"priceEstimate":null}`; пропущена ціна PATCH зберігає попередню, пропущена POST → null. Профіль, наприклад: `{"city":"Київ","category":"TECH_REPAIR","description":null}`. Зміна профілю не змінює Service.category.

DTO profile/master: id (MasterProfile), name (User), city, category, nullable description. DTO service: id, title, category, nullable description, nullable fixed-two-decimal priceEstimate, isActive. Catalog service додатково має `master` із public DTO. Значення грошей — **JSON string або null**, не number/Float. Публічна видача завжди active, приватна повертає поточний isActive для керування.

Валідація strict Zod:

- city: нормалізація пробілів, 1–100; title: нормалізація пробілів, 1–160; raw caps 200/320 відповідно.
- category: TECH_REPAIR / PLUMBING / ELECTRICAL / OTHER.
- description: nullable string до 2000 після trim; порожня → null.
- priceEstimate: nullable exact decimal string 0..99999999.99, максимум дві цифри після крапки; експонента/кома/NaN/number не приймаються. UI порожню ціну перетворює на null.
- isActive: тільки boolean, для POST типово true.
- unknown/protected поля, порожній PATCH, UUID/query overrides → 400 з field errors. Name/email/password/role/isApproved/masterProfileId/userId не редагуються.

Public city — буквальне case-insensitive порівняння з поточним MasterProfile.city; category — **Service.category**. q шукає case-insensitive substring у title або description, нормалізує пробіли, до 120 символів (raw cap 240). `%`, `_`, `\` екрановані як буквальні LIKE-символи, SQL-looking text лишається даними. Prisma параметризує значення. Порядок title ASC/id ASC; page типово 1, до 10000; limit типово 12, 1..50. Counts і сторінка читаються в RepeatableRead. Master-page query приймає тільки page/limit. Сторінка поза останньою повертає порожній services, без розширення ліміту.

| Помилка | Політика |
| --- | --- |
| 400 | Некоректні поля/UUID/query, зайві поля, порожній PATCH |
| 401 | Missing/invalid/expired JWT, видалений User на private маршруті |
| 403 | CLIENT/ADMIN або MASTER без профілю на private маршруті |
| 404 | Відсутня або чужа Service — **однакова відповідь**; відсутній public MasterProfile |
| 409 | Виявлений Prisma transaction write conflict/deadlock P2034: оновити й повторити |

Помилки — стандартний `{error:{code,message,fields?}}`, без SQL/stack/секретів. Звернутися до чужого профілю через PATCH із чужим ID неможливо: extra ID у body відхиляється, чужий profile path не існує. 409 mapping реалізовано; реальний DB deadlock цим прогоном спеціально не провокувався, frontend 409 перевірено HTTP mocks.

## Сумісність і транзакції

П’ять моделей і три міграції без змін. `src/orders/service.ts` та SQL triggers не редагувалися. Profile PATCH блокує власний профіль FOR UPDATE; це узгоджено з SHARE lock у respond(). Service PATCH блокує scoped owned row FOR UPDATE; createStandard() уже використовує SHARE lock для формування snapshots. Ownership і роль повторно перевіряються всередині транзакції, не беруться з payload. Однаковий 404 для чужого/відсутнього Service захищає приватний ресурс від enumeration.

Нове місто/основна категорія змінюють **майбутню** CUSTOM аудиторію та прямий respond guard. Історичні Orders, title/city/category/priceAtOrder/statusHistory не переписуються. STANDARD застосовується тільки як synthetic integration fixture для перевірки snapshots; публічних STANDARD orders/штучних production даних немає. Чинні CUSTOM offers/selection/lifecycle, CLIENT history та JWT/CORS/rate limits збережені.

## Залишені обмеження

- US-04/публічне STANDARD-замовлення ще недоступні; кнопка disabled, а не фіктивний success. Немає chat/ratings/photos/payments/ADMIN UI чи виправлення FIX-17.
- Зміни між вікнами видно після GET/refresh, без realtime. Пошук — literal substring, без fuzzy/aliases/геокодування. Для великих обсягів потрібна окрема оптимізація search indexes; нових міграцій тут немає.
- Власний список послуг без пагінації; обидва публічні списки мають hard limit 50. Повного optimistic versioning/ETag немає: одночасні редагування серіалізуються, останнє збереження виграє.
- POST не має idempotency-key. Після втрати відповіді потрібні GET і перевірка списку перед ручним повтором; автоматичного повтору немає.
- Для production static hosting потрібен history fallback на index.html для public direct URLs; Vite dev/F5 перевірено реальним browser. Windows виконання не заявляється.
