# US-06 / US-07 — пропозиції майстрів і вибір виконавця

База: develop після merge PR #5, `70617b94a81d89928f51d78df1cf8f123ed2b17d`.
Гілка: `feature/us-06-07-master-offers`. Дата перевірки: 15.11.2026, Codex Cloud/Linux.

## Реалізація

MASTER відкриває `/dashboard` → «Заявки для майстра» (`/master/orders`). Сервер читає поточний MasterProfile за JWT subject і повертає тільки OPEN CUSTOM без призначеного майстра, у його місті та категорії, createdAt DESC / id DESC. Місто порівнюється без регістру після trim профілю; символи `%`, `_`, `\` екрануються як буквальні символи PostgreSQL ILIKE. Категорія — точний enum. Query-параметри не можуть змінити аудиторію.

Форма надсилає лише текстову пропозицію. Наявний `respond()` у транзакції блокує профіль FOR SHARE і заявку FOR UPDATE, повторно перевіряє роль, стан, дубль та відповідність профілю. Тому прямий POST поза стрічкою теж не обходить правила. UNIQUE(order_id, master_profile_id) та чинні SQL triggers залишені. Друга/конкурентна пропозиція одного майстра → 409. Старі пропозиції не видаляються й не перекласифіковуються.

CLIENT у `/orders` натискає «Переглянути пропозиції». Запит виконується при відкритті, а не для кожної картки автоматично. Власник бачить текст і публічні дані майстра, може обрати одну пропозицію. Контролер викликає **наявний незмінений `selectResponse()`**, який блокує Order FOR UPDATE, перевіряє власника/OPEN/належність OrderResponse і атомарно записує masterProfileId, priceAtOrder та ACCEPTED. Другий одночасний запит → 409; подія ACCEPTED у statusHistory лише одна. ID майстра напряму не приймається.

Відповідь вибору одразу оновлює клієнтську картку й ім’я виконавця. На 409 виконується автоматичний GET пропозицій/поточного стану; повідомлення про конфлікт збережене. Якщо повторний GET не вдався, застарілий вибір заблокований до успішного retry. Порівняння statusHistory/updatedAt не дозволяє пізньому GET повернути старий OPEN після успішної мутації. 401 використовує чинний logout; FIX-17 не змінено.

MASTER бачить призначені йому CUSTOM у `/dashboard`, включно з кінцевими станами для збереження історії заявок. «Оновити призначення» перечитує сервер. Пропозиції інших майстрів та приватні дані клієнтів у MASTER DTO не повертаються.

## API

Усі маршрути нижче мають префікс `/api/v1` та потребують Bearer JWT. Поточна роль перевіряється з БД. MASTER routes змонтовані окремо від CLIENT-only `/orders` middleware.

| Метод і шлях | Доступ | Результат |
| --- | --- | --- |
| GET `/master/orders/available` | MASTER з профілем | 200 `{orders}`; серверний відбір, власна `myResponse` або null |
| GET `/master/orders/assigned` | MASTER з профілем | 200 `{orders}`; CUSTOM, призначені його профілю, найновіші першими |
| POST `/master/orders/:id/responses` | MASTER з відповідним профілем | 201 `{response}`; тільки `{message}` |
| GET `/orders/:id/responses` | CLIENT-власник CUSTOM | 200 `{order, responses}`; пропозиції від старих до нових |
| POST `/orders/:id/select-response` | CLIENT-власник OPEN CUSTOM | 200 `{order}`; тільки `{responseId}` |
| GET `/orders` | CLIENT | Збережений власний список; додано nullable `assignedMaster` |
| POST `/orders` | CLIENT | Збережене створення CUSTOM OPEN, 201 |
| DELETE `/orders/:id` | CLIENT-власник | Збережене логічне скасування, 200; виконавець та історія лишаються |

UUID у params/responseId перевіряється Zod. `message`: trim, 1–2000 символів, лише string. Body strict: userId/clientId/masterProfileId/status/proposedPrice та інші сторонні поля не дозволені. GET query strict, без клієнтських фільтрів.

- 400: некоректні UUID, поля, порожній/надто довгий message, query overrides; GET пропозицій STANDARD.
- 401: відсутній/недійсний/прострочений JWT, видалений User.
- 403: неправильна роль, відсутній MASTER-профіль, чужий CLIENT-власник, інше місто/категорія при новій пропозиції.
- 404: відсутня заявка; відсутня або належна іншій заявці пропозиція при виборі.
- 409: повторна пропозиція, неактивна/не-CUSTOM заявка для пропозиції, повторний/конкурентний вибір, закрита заявка.

Public master DTO: profile `id`, `name` із User, `city`, `category`, nullable `description`. Не включає email, passwordHash, userId, isApproved. MASTER Order DTO не включає clientId, User metadata чи audit actor IDs. Власний CLIENT Order зберігає попередній контракт, включно зі statusHistory, та додає `assignedMaster`. Грошові значення — decimal strings або null, не Float. Публічний POST пропозиції ціни не запитує; nullable proposedPrice у чинній моделі збережене для старих даних/внутрішніх команд.

Жоден попередній тест чи assert не видалений; profile B відновлюється через finally. Нова перевірка аудиторії не послаблюється для seed/test accounts.

Тому нові integration/browser synthetic cohort і committed історії залишаються **тільки в ізольованій *_test БД** для перевірки, як і попередній concurrency test. Повторні прогони використовують випадкові email/міста; глобальна кількість записів може зростати. Старі seed proposals збережені без міграції, навіть якщо вони не відповідають новому правилу для створення пропозиції.

## Windows 11 / PowerShell QA

Потрібні Node 24/npm 11, PostgreSQL 18 і psql у PATH. Створіть **нову окрему** локальну БД `fixit_offers_test` з власною обмеженою тестовою роллю через адміністратора PostgreSQL; не використовуйте fixit_dev. Роль/БД, якщо вже існують, не видаляйте. Налаштуйте приватний `.env` за `.env.example`: DATABASE_URL і TEST_DATABASE_URL вказують саме на дозволену loopback *_test БД, SHADOW_DATABASE_URL — на іншу БД. JWT_SECRET згенеруйте локально, тримайте поза Git/скріншотами. Деталі створення ролі — README.

```powershell
git fetch origin
git switch feature/us-06-07-master-offers
npm ci
npm run db:generate
npm run db:validate
npm run db:migrate
npm run db:status
npm run typecheck
npm test
npm run frontend:test
npm run frontend:build
npm run frontend:coverage
npm exec playwright install chromium
npm run test:e2e
```

Не задавайте Linux PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH на Windows. E2E запускає сервери 4100/5174 самостійно, із випадковим environment JWT secret. Для ручної QA: у першому терміналі `npm run dev`, у другому `npm run frontend:dev`; frontend 127.0.0.1:5173, API 127.0.0.1:3000. Використовуйте один hostname для CORS. Фактичне виконання Windows тут не заявляється.

1. Зареєструйте синтетичного CLIENT і двох MASTER із однаковими містом/категорією; для негативної перевірки — MASTER з іншим містом/категорією. Використовуйте власні тестові паролі.
2. CLIENT → «Мої заявки» → створіть CUSTOM у цьому місті/категорії. Збережіть order UUID з Network response.
3. В окремих браузерних профілях/вікнах увійдіть як MASTER, відкрийте стрічку. Відповідні MASTER бачать заявку, інший профіль не бачить і отримує 403 на прямий POST. Надішліть дві різні текстові пропозиції. Повторний POST одного майстра → 409.
4. CLIENT відкриває пропозиції та обирає одну. Network POST select-response → 200; картка стає «Прийнята», показує ім’я виконавця. Повторний запит → 409. Чужий CLIENT → 403.
5. Обраний MASTER відкриває кабінет/«Оновити призначення»: є ACCEPTED. Інший MASTER не має цієї заявки серед призначених. F5 потребує нового входу (FIX-17, відомо).
6. Для перевірки БД виконайте наведений SELECT у psql, підставивши лише synthetic UUID. Не знімайте вивід `.env`/паролів/JWT.

```sql
SELECT id, type, status, master_profile_id, status_history
FROM orders WHERE id = '<synthetic-order-uuid>';
SELECT id, order_id, master_profile_id, message
FROM order_responses WHERE order_id = '<synthetic-order-uuid>';
```

Можливі реальні докази: (1) CLIENT картка з пропозиціями/«Прийнята», (2) Network POST response 201 та select-response 200 без видимого Authorization, (3) MASTER кабінет і SQL SELECT з тим самим order UUID. Ці локальні screenshots не вигадуються й не додаються автоматично.

## Межі

- FIX-17: JWT лише в пам’яті, F5 завершує клієнтську сесію; механізм не змінено. FIX-18 регресія пройшла.
- Без realtime, pagination, пошуку/словника міст чи геокодування. Інша сесія має натиснути «Оновити»; регістр і trim не уніфікують різні назви одного міста.
- Призначені заявки показують поточний статус; повний timeline/дії виконання робіт не додаються. Публічна пропозиція текстова, без редагування/відкликання/цінових переговорів.
- Без нових таблиць/міграцій, chat/payments/ratings/notifications, ADMIN UI або змін JWT. PR потребує review; автоматичного merge немає.
