## Поведінка та межі

Призначений MASTER у `/dashboard` починає ACCEPTED-заявку, потім завершує IN_PROGRESS. Статус оновлюється у React з відповіді PATCH без F5. Для COMPLETED показано відому дату завершення й немає дій; CANCELLED/DECLINED теж без дій виконання. CLIENT після «Оновити» у `/orders` бачить «У роботі»/«Завершена»; після початку немає кнопки скасування, прямий DELETE теж повертає 409.

Контролер використовує **наявний незмінений `createOrderService().transition()`**. Він читає actor/роль/профіль із БД, блокує Order FOR UPDATE, перевіряє виконавця й дозволений перехід та виконує UPDATE у транзакції. Наявний SQL trigger додає одну подію з actorUserId із transaction-local контексту; HTTP-контролер не пише історію самостійно й не дублює матрицю переходів.

Конкурентні однакові PATCH → один 200, один 409, одна подія. Кнопки й оновлення списку блокуються на час мутації. 409 і неоднозначні помилки PATCH (мережа/5xx тощо) автоматично запускають GET assigned зі збереженням повідомлення. Це враховує випадок, коли commit уже відбувся, а відповідь втрачено: **PATCH автоматично не повторюється**. Якщо GET також не вдався, картка лишається й дії заблоковані до успішного «Оновити призначення». 401 використовує чинний logout; 403 блокує повторну мутацію відповідної картки навіть після GET у цій сесії компонента.

**Це не повне закриття US-08/FIX-8:** публічний STANDARD flow залежить від US-04. Наявний `transition()` і новий API підтримують PENDING → ACCEPTED/DECLINED; це перевірено на синтетичних STANDARD integration fixtures. Публічні STANDARD форми, створення замовлень, кнопки приймання/відхилення чи нові таблиці не додані. Assigned GET/UI лишаються CUSTOM. FIX-9 покрито частково: стан і відома дата у списку CLIENT; новий повний timeline не реалізований.

## API-контракт

`PATCH /api/v1/master/orders/:id/status`

Headers: `Authorization: Bearer <session JWT>`, `Content-Type: application/json`. Тільки поточний MASTER; ID — виключно JWT subject та профіль із БД. UUID params, порожній query й strict body перевіряються Zod.

```json
{ "status": "IN_PROGRESS" }
```

Body приймає один `status` із чинного enum: OPEN, PENDING, ACCEPTED, IN_PROGRESS, COMPLETED, CANCELLED, DECLINED. Валідне enum-значення ще не означає дозволений перехід: це вирішує виключно `transition()`. Для призначеного CUSTOM доступні тільки ACCEPTED → IN_PROGRESS та IN_PROGRESS → COMPLETED; MASTER не отримує право скасування.

200: `{ "order": <safe MASTER Order DTO> }`. Поля DTO: id, type, status, title, description, city, category, budget (decimal string/null), createdAt, updatedAt, completedAt (ISO string/null). Не повертаються clientId, email, passwordHash, userId, isApproved, raw statusHistory чи audit actor IDs. Власний CLIENT Order DTO на старих GET/POST/DELETE routes також додає completedAt, зберігаючи попередні поля/історію/assignedMaster.

| HTTP | Причина |
| --- | --- |
| 400 | Невалідний UUID/enum/body/query; зайві userId/masterProfileId/clientId/statusHistory та інші поля |
| 401 | Missing/invalid/expired JWT, token іншого підписувача або видалений account |
| 403 | CLIENT/ADMIN, чужий MASTER, профіль відсутній або MASTER не призначений |
| 404 | Немає заявки з цим UUID (для авторизованого MASTER) |
| 409 | Повторний, пропущений, конкурентний чи недозволений перехід, кінцевий стан |

Помилки мають стандартний `{error:{code,message,fields?}}`, без SQL/stack/секретів. CORS додано PATCH зі збереженням точних origins, дозволених headers і чинного JWT middleware.

`completedAt` не є новою колонкою: значення виводиться тільки з валідної `COMPLETED` події `statusHistory`, `source=database`. Дата нормалізується до ISO UTC із мілісекундами. `legacy_migration` є спостереженням на час міграції, тому не використовується як реальна дата завершення. Відсутня/некоректна подія → null; createdAt/updatedAt/current time не підставляються.

На Windows не задавайте Linux PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH. Browser suites самі запускають test servers 4100/5174 із випадковим secret. Для ручного сценарію: перший термінал `npm run dev` (API 127.0.0.1:3000), другий `npm run frontend:dev` (UI 127.0.0.1:5173). Один hostname для CORS.

1. У двох окремих браузерних профілях зареєструйте синтетичних CLIENT і MASTER. Для MASTER задайте місто/категорію, які потім вкажете у CUSTOM. Увійдіть в обох профілях.
2. CLIENT із кабінету відкриває «Мої заявки», створює CUSTOM. MASTER через «Заявки для майстра» надсилає текстову пропозицію. CLIENT відкриває пропозиції та обирає її.
3. MASTER повертається до кабінету через посилання, за потреби натискає «Оновити призначення». ACCEPTED → «Розпочати роботу». Network PATCH містить лише status=IN_PROGRESS і повертає 200; картка стає «У роботі» без F5.
4. CLIENT натискає «Оновити»: «У роботі», кнопки скасування немає. Прямий DELETE з JWT цього CLIENT повертає 409, запис лишається.
5. MASTER натискає «Завершити роботу»: PATCH status=COMPLETED → 200, «Завершена» й дата, дій більше немає. CLIENT після оновлення бачить ті самі стан/дату; заявка лишається в історії.
6. Інший MASTER → PATCH 403; CLIENT → MASTER PATCH 403. Пропуск ACCEPTED → COMPLETED чи повторний PATCH → 409. Для UI-конфлікту відкрийте той самий кабінет у двох окремих сесіях MASTER: одна починає, друга зі старою карткою отримує 409 і автоматично оновлюється.
7. Для реальних доказів зніміть MASTER «Завершена»/дату, CLIENT оновлений список та Network 200 без видимого Authorization. Перевірте SQL нижче, підставляючи лише synthetic UUID. Не знімайте паролі/JWT/.env.

```sql
SELECT id, type, status, master_profile_id, created_at, updated_at, status_history
FROM orders WHERE id = '<synthetic-order-uuid>';
SELECT event->>'status' AS status, event->>'at' AS changed_at,
       event->>'actorUserId' AS actor, event->>'source' AS source
FROM orders, LATERAL jsonb_array_elements(status_history) AS event
WHERE id = '<synthetic-order-uuid>';
```

Очікується OPEN → ACCEPTED → IN_PROGRESS → COMPLETED, останні дві події від User.id призначеного MASTER; одна подія кожного стану. Дата DTO — остання справжня COMPLETED-подія, нормалізована до мілісекунд UTC. **F5 потребує повторного входу (FIX-17)** — у QA використовуйте навігацію всередині застосунку. Немає realtime/pagination, full timeline, US-02/03/04, chat/payments/notifications або нових адміністративних функцій.
